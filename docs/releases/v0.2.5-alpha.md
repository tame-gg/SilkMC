# SilkMC v0.2.5-alpha

SilkMC v0.2.5-alpha is a correctness release on the Minecraft **26.2** baseline. It fixes the
plugin compatibility scanner refusing to load correct plugins, removes off-region game state
access from the status bars added in `v0.2.2-alpha`, and adds the project's first unit tests.

There are no new features and no configuration changes.

## Behaviour change: correct plugins are no longer refused

The compatibility scanner classified plugins by searching the raw bytes of every class in the jar
for text such as `isPrimaryThread` or `org/spigotmc/AsyncCatcher`. Raw bytes include string
literals, resource names and every other piece of text in the constant pool, so a jar that merely
*mentioned* one of those - in a log message, a config key, or a shaded library - matched.

The consequence was not a bad classification but a refusal to start. `isPrimaryThread` produced an
`UNSAFE` classification, and `UNSAFE` is a hard block. A plugin that called
`Bukkit.isPrimaryThread()` defensively, or shaded any library that named it, was rejected outright
with no way to tell a real hit from a coincidence except an operator override.

The scan is now structural. Each class is parsed and only genuine symbol references are considered:
supertypes and interfaces, field and method descriptors, and the owner and name of every
instruction that touches a type or calls a method. Text in a string constant or a resource is no
longer a signal.

The classification boundaries moved with it:

- `UNSAFE` now means a real reference to `org/spigotmc/AsyncCatcher`, which has no purpose other
  than disabling the thread checks the server depends on. This remains a hard block.
- A call to `isPrimaryThread()` is now `UNKNOWN` rather than `UNSAFE`. The usual reason to ask
  whether you are on the main thread is to be careful about threading; that deserves an operator's
  attention, not a refusal. Under the default `WARN` policy such plugins now load with a warning.
- A jar that cannot be read, or a class that cannot be parsed - for example one compiled for a
  newer class-file version than the server's bytecode reader knows - is now `UNKNOWN` with an
  explicit reason. Previously an unreadable jar aborted plugin loading with a raw exception, and
  the absence of signals from unparseable classes was indistinguishable from a clean scan.

Operators running with `unsupported-plugin-mode: REQUIRE_DECLARATION` should expect to see plugins
that previously failed as `UNSAFE` now appear as `UNKNOWN`, which that mode still blocks. Under the
default `WARN` mode they will load.

Force-loading a plugin classified `UNSAFE` now always logs a warning. Previously the only trace was
an informational line, despite it being the riskiest thing an operator can configure here.

## Fix: status bars no longer read game state off-region

`/tpsbar` and `/rambar`, added in `v0.2.2-alpha`, refreshed every tracked player from a single
private daemon thread that owned no region. Once a second it called `getWorld()`, `getLocation()`,
`getPing()` and `showBossBar()` on players being ticked concurrently by their own regions, and
looked each player's chunk up in the regioniser to find tick data - the exact pattern SilkMC
classifies third-party plugins as unsafe for.

Each tracked player now drives their own refresh loop through their entity scheduler, so every read
happens on the region that owns that player. The scheduler follows the player across region splits,
merges and dimension changes, and retires the loop on disconnect. Because the callback already runs
on the player's region, the tick report is read from the region being ticked rather than looked up
by position, which also closes the window where a player had moved to a different region than the
one being reported.

A supervisor thread still ticks once a second, but it touches no game state: it hands a task to the
global region, which owns the player list and can safely arm a loop for anyone who has opted in but
is not running one. Toggles from the two commands are funnelled onto the owning region as well,
which removes a race that could show a player two overlapping bars.

## Fix: files are resolved against the server directory

`silkmc-compatibility.yml`, `silkmc-plugin-overrides.yml` and the status bar opt-in file
`silkmc-status-bars.json` were opened by bare relative name, which resolves against the process
working directory rather than the server directory. These are usually the same. When they are not,
the server read and created defaults in a different set of files from the ones sitting next to
`server.properties`, and `/silkmc reload` reported success having reloaded nothing the operator had
changed. All three now resolve against the server directory.

The status bar file is also written through a temporary file and moved into place, so losing the
process partway through a write can no longer leave a truncated file. A half-written file does not
parse, which previously dropped every player's opt-in rather than just the toggle in flight.

## Fix: scoreboard registry pruning

The weak registry of plugin scoreboards, added in `v0.2.4-alpha`, removed collected entries as an
iterator encountered them. That is correct but each removal copies the whole backing array, so a
single criteria update after a mass disconnect walked it quadratically on a region thread, with
every region contending on the same copy-on-write lock.

Cleared references are now enqueued by the collector and removed as one batch when a scoreboard is
next registered. Iteration - the hot path, reached by every health, death and kill-count update -
only skips them. Registering the same scoreboard twice is now also a no-op; previously it applied
every criteria update to that scoreboard twice.

## Fix: locale-dependent policy parsing

`unsupported-plugin-mode` was uppercased using the host's default locale before being matched. Under
a Turkish locale `require_declaration` uppercases to `REQUİRE_DECLARATION`, which does not match,
and the parse fell back to `WARN`. A server configured to require explicit compatibility metadata
silently stopped requiring it depending on where it was running.

Compatibility failure reporting also walked a plugin's exception cause chain with only a
single-hop cycle guard, so a cyclic cause chain could hang the reporting thread while the server
was already handling a failure. The walk is now bounded.

## Tests

SilkMC's own logic now has unit tests - 50 of them, run by `./gradlew build` and therefore in CI on
every push and pull request. They cover the compatibility scanner (including the string-constant
false positive above, as an explicit regression test), the classification rules, the weak scoreboard
registry under concurrent readers and writers, and the status bar formatting and thresholds.

This matters more than the count suggests: SilkMC is maintained as a patch set rebased onto upstream
Folia, and this is the logic most likely to break quietly during a version bump.

## Upgrade notes

Drop-in. No configuration changes are required.

Operators who added `silkmc-plugin-overrides.yml` entries to work around the scanner rejecting a
plugin should re-check whether they are still needed - many were compensating for the false
positives fixed here. Overrides that are no longer needed can be removed; `/silkmc report <plugin>`
shows the classification a plugin now receives.

Anyone launching the server from a directory other than the server directory should move
`silkmc-compatibility.yml`, `silkmc-plugin-overrides.yml` and `silkmc-status-bars.json` next to
`server.properties` if they are not already there.
