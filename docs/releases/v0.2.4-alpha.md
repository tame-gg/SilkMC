# SilkMC v0.2.4-alpha

SilkMC v0.2.4-alpha builds on the Minecraft **26.2** baseline from `v0.2.3-alpha` and restores
the Bukkit/Paper scoreboard API, which has been unavailable since the fork inherited Folia's
region threading. Plugins that use scoreboards now work without SilkMC-specific code, and the
vanilla `/scoreboard` command is available again with region-aware selectors.

## Feature: the Bukkit scoreboard API works again

Folia disabled the scoreboard API behind five `UnsupportedOperationException` guards, so any
plugin calling `Bukkit.getScoreboardManager().getNewScoreboard()`, `registerNewObjective`,
`registerNewTeam`, `clearSlot`, or `Player#setScoreboard` failed outright. Scoreboard
synchronisation on join, scoreboard cleanup on entity removal, and the player-collision team
were commented out for the same reason.

The implementation itself was never missing. The blocker was thread safety: `Scoreboard`,
`PlayerScores`, `PlayerTeam` and `Score` store their state in non-concurrent collections and
non-volatile fields, and every region thread reaches that state. The registry of plugin
scoreboards was an `ArrayList`-backed `WeakCollection` walked on every criteria trigger.

Notably, this was already a live problem before this release rather than only a
plugin-facing one: criteria objectives such as `health`, `deathCount` and `playerKillCount`
have always updated the main scoreboard from region threads through those same
non-concurrent collections. Disabling the plugin-facing API never made that safe.

### What changed

Scoreboard state is now held in concurrent collections, with a per-scoreboard lock used only
for compound structural mutations - creating an objective, moving a player between teams,
removing an objective - so those stay atomic without reintroducing a global server thread. No
packets are sent while that lock is held.

Region-owned side effects are scheduled rather than run inline. Waypoint reconnection, which
touches world state owned by a specific region, is routed through the affected player's task
scheduler. Assigning a scoreboard to a player flips the assignment immediately, so
`getScoreboard()` is coherent for the caller, but orders the teardown-and-resync packet burst
on that player's owning thread so it cannot interleave with join synchronisation or a
concurrent switch.

Packet broadcast is left direct, since the player list is copy-on-write and channel writes are
thread-safe. `AsyncCatcher` is retained, so scoreboard calls from genuinely asynchronous
plugin threads are still rejected exactly as on Paper.

Scoreboard synchronisation on join has been restored, and now sends the player's own board
rather than the level's, so a scoreboard assigned during `PlayerJoinEvent` is honoured.

## Feature: `/scoreboard` is available again, with region-scoped selectors

The vanilla `/scoreboard` command was disabled entirely. It is now registered.

Scoreboard state is safe to touch from any region thread, but a score holder that is a live
entity is not - selector resolution walks every level, and neither the selector nor the entity
getters assert region ownership, so an unfiltered `@a` or `@e` reads entity state that another
region may be ticking concurrently.

Every `/scoreboard` subcommand resolves its targets through `ScoreHolderArgument`, so the
scoping is applied at that single point. Score holders that are not entities - plain names,
`#hidden` names, offline players, the `*` wildcard - carry no entity state and always pass,
which covers the overwhelming majority of scoreboard usage. Entity holders are kept only when
the executing thread owns them. A command that matches some out-of-region entities reports
what it skipped; one that matches *only* out-of-region entities fails rather than silently
doing nothing.

This also covers `/execute ... score`, which shares the same argument type and was already
enabled with its selectors unguarded.

`/team` and `/trigger` remain disabled.

## Behaviour change: player collisions

Paper's `enable-player-collisions: false` option works again. The collision team it relies on
was being created, but the code adding and removing players from it was disabled under region
threading, so the setting silently had no effect. Servers that set this option to `false` and
had grown used to collisions remaining on will now see collisions actually disabled.

## Upgrade notes

No configuration changes are required. Plugins that were shipping SilkMC-specific workarounds
for the missing scoreboard API can drop them; the standard Bukkit/Paper API is the supported
path.
