# SilkMC v0.2.3-alpha

SilkMC v0.2.3-alpha builds on the Minecraft **26.2** baseline from `v0.2.2-alpha` and
hardens the plugin lifecycle so that a plugin which fails to enable can no longer spam the
console with a second, misleading crash while it is being torn back down.

## Fix: cascading `onDisable` failures no longer look like a crash

When a plugin's `onEnable` throws, Paper immediately disables the plugin again by calling its
`onDisable`. A plugin that failed partway through `onEnable` is only half-initialised, so its
own shutdown logic very often trips over its own uninitialised state and throws a **second**
exception — most commonly a `NullPointerException` on a field that `onEnable` never got to
set. Before this release SilkMC logged that follow-up failure as a raw `SEVERE` stack trace,
which reads like an independent crash even though the server has already handled the situation.

A representative example is **NoChatReports v2.7.8**, which could not resolve an NMS provider
for this SilkMC/Minecraft version. Its `onEnable` failed, and the subsequent
Paper-initiated disable then hit:

```
Error occurred while disabling NoChatReports v2.7.8
java.lang.NullPointerException: Cannot invoke
  "com.tcoded.nochatreports.nms.NmsProvider.getChannelInjector()"
  because "this.nmsProvider" is null
    at com.tcoded.nochatreports.plugin.NoChatReports.onDisable(NoChatReports.java:167)
    ...
```

### What changed

SilkMC now recognises this shutdown exception as a **cascade of the enable failure that was
already reported**, rather than a new, actionable problem:

- When a plugin throws during enable, SilkMC flags it (`SilkPluginCompatibility.markEnableFailed`)
  right before Paper disables it.
- If that same plugin then throws from `onDisable` during the immediately following disable,
  SilkMC (`SilkPluginCompatibility.handleDisableFailure`) logs a single, concise, operator-facing
  line explaining that the shutdown error is a side effect of the earlier enable failure, is
  safe to ignore, and that the server has disabled the plugin and kept running. The raw stack
  trace is kept at `FINE` so the default console stays clean, while remaining available when
  SilkMC debug logging is enabled.
- Disable failures for plugins that enabled successfully are **unchanged** — they still log at
  `SEVERE` with the full stack trace, so genuine shutdown bugs are not hidden.

This does not make an incompatible plugin work — NoChatReports still needs a build that
supports this SilkMC/Minecraft version — but the server no longer prints a scary second
stack trace, and other plugins continue to enable normally.

## Notes

- The Minecraft `26.2` baseline (`mcVersion`/`apiVersion` `26.2`, Paper base
  `2717585e686d7d294cabce9f1753280780ecf847`) and all 26.2 region-threading patches and
  compatibility features from `v0.2.0-alpha` through `v0.2.2-alpha` are preserved and
  unchanged.
- The change lives in the maintained SilkMC compatibility layer
  (`gg.tame.silkmc.server.compat.SilkPluginCompatibility`) and the plugin lifecycle hook in
  `io.papermc.paper.plugin.manager.PaperPluginInstanceManager`
  (patch `silkmc-server/paper-patches/features/0008-SilkMC-compatibility-improvements.patch`).

## Build

```powershell
$env:JAVA_HOME='C:\Program Files\Eclipse Adoptium\jdk-25.0.2.10-hotspot'
$env:Path="$env:JAVA_HOME\bin;$env:Path"
./gradlew applyAllPatches
./gradlew build
./gradlew :silkmc-server:createPaperclipJar
```

Run with:

```powershell
java -Xms4G -Xmx4G -jar .\silkmc-server\build\libs\silkmc-paperclip-26.2.local-SNAPSHOT.jar nogui
```
