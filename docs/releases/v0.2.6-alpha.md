# SilkMC v0.2.6-alpha

SilkMC v0.2.6-alpha is a threading and correctness release on the Minecraft **26.2** baseline. It
raises the default tick thread count, fixes four region-threading defects in state shared between
regions, restores five vanilla commands, and adds a benchmark harness for measuring region
workloads.

**This release changes a default.** Servers that have not set `threaded-regions.threads` will use
more tick threads than before. See below.

## Default change: tick thread count

`threaded-regions.threads`, when unset, now resolves to `cores / 4` (minimum 1) instead of the
upstream Folia formula.

Upstream halves the core count and then divides by four, which collapses to a single tick thread on
any machine with 8 or fewer usable cores - and, because `6 / 4` truncates, on 12-core machines as
well. A 32-core machine received 4 threads.

| Cores | Before | Now |
| --: | --: | --: |
| 6 or fewer | 1 | 1 |
| 8 | 1 | 2 |
| 12 | 1 | 3 |
| 16 | 2 | 4 |
| 32 | 4 | 8 |
| 64 | 8 | 16 |

Measured on a 12-core machine with the benchmark harness added in this release - 8 regions running a
mixed hopper, redstone and entity workload requiring roughly 2.4 threads' worth of work - one tick
thread sustained **10.03 TPS** while two sustained **19.90**. With the new default the same machine
selects 3 threads and holds **19.95 TPS**.

The failure this fixes was silent, which is the important part. A region that cannot keep up skips
ticks, and the ticks it does complete are the cheap ones. The single-thread configuration therefore
reported the **lowest average MSPT of any configuration tested** - 12.8 ms, against 18.1 ms at 8
threads - while running at half speed. An operator diagnosing this with `/tps` would have seen an
apparently healthy server.

Average MSPT rises with this change (12.81 ms to 14.16 ms on the workload above). That is the
expected result of completing every tick rather than dropping work, not a regression.

`cores / 4` leans deliberately high, because the two errors are not symmetric: under-provisioning
cost half the tick rate, while over-provisioning cost only CPU - summed region utilisation rose 1.39
to 1.57 going from 2 to 4 threads at identical TPS. Three quarters of the machine remains available
to the chunk system, Netty, GC workers and the global region.

Setting `threaded-regions.threads` explicitly continues to override this entirely. Operators who
have already tuned it are unaffected.

## Region threading fixes

Four defects in state that is mutated on one region thread and read from others. All four are
correctness fixes; none changes behaviour that was previously correct.

- **World border.** `WorldBorder` had no volatile fields, despite being mutated on the global region
  and read by every region thread on movement and collision paths. Because a moving border swaps in
  a new `BorderExtent`, the unsafely published value was an object reference rather than a scalar,
  so a region thread could observe a partially constructed border.
- **Scoreboard objective removal.** Removing an objective raced with `PlayerScores#getOrCreate`,
  which reads without a lock on the criteria hot path. A score could be created for an
  already-removed objective and left behind. Fixed with a publish-then-verify handshake, so the hot
  path remains lock-free.
- **Boss bars.** `ServerBossEvent` held a plain `HashSet` of players and `BossEvent`'s fields were
  non-volatile, while `CraftBossBar` allows any plugin to mutate a bar from any region thread. This
  affected the **Bukkit BossBar API** independently of the `/bossbar` command, so it was reachable
  on any server running a plugin that uses boss bars.
- **Legacy scheduler task lifecycle.** Sync tasks bridged onto Folia's schedulers were never removed
  from `CraftScheduler#runners`, because `mainThreadHeartbeat` is the only path that removes them and
  it does not run under SilkMC. On a server with plugins using `runTask` and friends, this grew
  without bound.

`CraftServer#getTPS` and `#getAverageTickTime` also no longer throw when called off a region thread;
they fall back to the global region's tick data.

## Restored commands

`/team`, `/teammsg`, `/trigger`, `/tag` and `/bossbar` are available again. Each was assessed for the
state it touches and which thread owns that state, rather than restored because it was commented
out:

- `/tag` and `/trigger` may target entities owned by another region, so their targets are filtered
  through the existing region-scoped resolution, which reports what it skipped rather than acting
  cross-region silently.
- `/team` reuses the existing scoreboard write lock rather than introducing a second concurrency
  mechanism, and team creation is atomic.
- `/bossbar` depends on the boss bar fix above.

## Benchmark harness

`tools/benchmark` generates a deterministic, client-free region workload and samples the tick
statistics the server already maintains. It has no external dependencies and adds no instrumentation
to the tick loop - the `/silkmc bench` subcommand only formats windows that are collected on every
region tick regardless.

It reports TPS alongside MSPT, and reports it first, because MSPT alone will report a saturated
server as the healthiest configuration in a matrix.

See `tools/benchmark/README.md` for what it does and does not measure. It cannot exercise connection
ticking or anything that scales with player count, since those paths require real clients.

## Documented, not changed

Investigations that concluded no code change was warranted are recorded rather than acted on:

- **Legacy sync scheduler tasks stay on the global region** (`docs/compatibility.md`). This is
  deliberate, not a gap awaiting more context: `runTask` and friends promise that tasks run in order
  and never concurrently with one another, and the global region is what still provides that.
- **Global region scaling limits** (`docs/architecture.md`). `PlayerList.tick()` is O(n²) in player
  count every 600 ticks, `tickConnections()` scans all connections even when nearly all are
  region-owned, and `autoSaveMaps()` performs synchronous disk I/O on the global tick thread. None is
  measurable without connected clients, so none was changed.
- **Allocation.** Profiling the saturating workload attributes roughly 0.2% of sampled allocation to
  SilkMC and Folia frames; the remainder is vanilla ticking. There is no per-tick allocation hot spot
  in SilkMC's own code to address.
- **GC pauses.** Reducing the young generation from the sizing in `docs/benchmarking.md` roughly
  halves the worst stop-the-world pause (119 ms to 65 ms). Whether that improves the observed tick
  tail is **not** established - a first pair of runs suggested it did and a confirmation pair showed
  no difference - so no default was changed and no tail-latency improvement is claimed.

## Upgrade notes

- Servers that have not set `threaded-regions.threads` will use more tick threads. On machines with
  8 or more cores this should raise sustained TPS under load; average MSPT will typically rise with
  it, as described above.
- Set `threaded-regions.threads` explicitly to keep the previous behaviour.
- No API changes. No configuration keys added or removed.
